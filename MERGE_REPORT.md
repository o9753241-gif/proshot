# Как собран server/ — отчёт о сведении двух копий

Этап 2 плана. Ничего в папке `ProShot` не менялось: она читалась.

## Из чего собрано

За основу взят `ProShot/_audit_server` — снимок боевой машины. Что это
действительно он, подтверждает `patch_server.sh`: скрипт пишет `prompts.py`
прямо в `/root/backend`, и содержимое в снимке совпадает с тем, что он пишет.

Единственная замена — `services/google_play.py`, взят из `ProShot/backend/app`.

| Файл | Откуда | Почему |
|---|---|---|
| `routers/generation.py` | снимок сервера | Списание фото, лимит 15/час, чистка медиа. В репозитории этого нет вовсе. |
| `models.py` | снимок сервера | Есть таблица `GenerationEvent`, без неё лимит не считается. |
| `routers/styles.py` | снимок сервера | 47 сцен по 7 вариантов одежды. В репозитории те же 47 сцен, но по одному варианту. |
| `services/prompts.py` | снимок сервера | Короткий сборщик + рост и вес. Идёт в паре с вариантами из `styles.py`. |
| `services/dashscope.py` | снимок сервера | `watermark: False` и случайный seed. |
| `services/google_play.py` | **репозиторий** | В снимке сервера на этом месте заглушка. Ради этого сведение и делалось. |
| остальные файлы | совпадали в обеих копиях | — |

## Что было в снимке сервера на месте проверки покупок

```python
if not settings.google_service_account_json or not os.path.exists(...):
    # DEV: доверяем клиенту
    return VerifyResult(ok=True, order_id=f"dev_order_{purchase_token[:8]}")
# TODO: подключить google-api-python-client и реальную проверку
return VerifyResult(ok=False, reason="real verify not wired yet")
```

Без файла сервисного аккаунта пакет фото получает любой, кто отправит запрос
на `/api/v1/billing/verify`. С файлом — не работает вообще. Если этот код
действительно сейчас на боевой машине, это дыра и в Android-версии.
Проверяется одной командой на VPS:

```
grep -n "real verify not wired" /root/backend/app/services/google_play.py
```

## Три правки, сделанные в этой копии

Все три — только здесь. Боевой Android-код не тронут.

1. **`main.py` — один обработчик `/health` вместо двух.** На сервере их два:
   информационный и добавленный позже с проверкой базы. FastAPI отдаёт первый
   совпавший, поэтому проверка базы никогда не выполнялась — мониторинг видел
   «ок» при мёртвой базе. Заодно база берётся из настроек, а не из зашитого
   `/root/backend/proshot.db`: у iOS-инстанса она своя, и зашитый путь заставил
   бы его проверять чужую.

2. **`routers/generation.py` — `get_prompt(scene_key, user.device_id)`.**
   Ротация вариантов одежды рассчитана на счётчик по устройству, но вызов шёл
   без второго аргумента, и все пользователи сидели в общем ведре `_shared`.
   Варианты вычёркивались вперемешку: в одной серии снимков костюм мог
   повториться, а другой не выпасть вовсе — ровно то, ради чего варианты и
   заводились.

3. **`config.py` — поле `allow_unverified_purchases: bool = False`.**
   `google_play.py` читал его через `getattr(settings, ..., False)`, а поля в
   `Settings` не было, то есть ветка «доверять клиенту» не включалась никогда.
   Поле заведено явно, значение по умолчанию сохраняет то же поведение.

Плюс в `requirements.txt` добавлены `google-api-python-client` и `google-auth`:
`google_play.py` их импортирует, а в списке зависимостей Android-проекта их не было.

## Что осталось решить

- **Пара «промпты + сцены».** Две связные конструкции, и половинки не
  смешиваются. На сервере: сцена описана внутри каждого из 7 вариантов
  (фон, свет, одежда, выражение), а `prompts.py` добавляет только кадрирование
  и телосложение. В репозитории наоборот: скупая строка сцены и большой сборщик
  с требованиями к идентичности, свету, оптике и текстурам. Взята серверная
  пара — она сейчас живая. Решение можно поменять до развёртывания.
- **Число вариантов одежды.** Семь штук закрывают Базовый пакет (около 7 фото
  на сцену). В Стандарте выходит ~10 на сцену, в Премиуме ~15 — одежда пойдёт
  по второму и третьему кругу. Не ошибка, цикл сбрасывается сам.
- **Что делать с Android.** Правки 1 и 2 применимы и к боевому инстансу, но
  это отдельное решение.
